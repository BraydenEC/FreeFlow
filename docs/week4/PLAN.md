## 1. Problem — what user problem is this solving?

FreeFlow is free and needs users, and has no marketing engine. There is
nothing a founder can actually post, no documented brand, no persona artefact,
no campaign, and no way to produce, save, or export marketing copy. A product
with no distribution is the donation-funnel problem restated: good work that
nobody sees. Week 4 builds the engine that turns the product into posts.

There is a second, honest problem. Marketing copy is the easiest place in a
project to lie — to a prospect and to yourself. The same discipline that made
the pricing simulator refuse to flatter applies here: claims on the marketing
page must trace to something real (the validated persona, the built features),
and generated copy must be labelled as generated.

## 2. User — who will use it?

Two users, and the page serves both.

| User | Need |
|---|---|
| **Brayden as marketer** | Ready-to-post content and a 14-day calendar, produced fast, exportable |
| **The prospective freelancer** | A credible landing page that says what the product is and is not |

The persona is validated rather than invented — it is the Week 2 interviewee:
a per-project installer who finds clients by cold outreach, called the UI
"annoying on mobile", and said he would rather rent something maintained than
build it. The marketing voice is built to reach that person, not a generic
"freelancer".

## 5. Scope cut — what looked nice but will not be built

| Cut | Why |
|---|---|
| Real email/social publishing (Buffer, Mailchimp, X API) | The assignment is a content *engine*, not a *publisher*. Posting is a different product — the same reasoning that cut Stripe checkout from Week 3. |
| Image generation for the posts | Text content only. Generating post images is a separate capability and a cost. |
| Analytics on the A/B test | The test picks a winner and records it. Impression/click tracking needs traffic that does not exist yet — inventing it would be the Week 3 CAC mistake. |
| A brand-new visual identity | The product already has a visual language. Week 4 documents and consolidates it, it does not replace it. |

## 7. Architecture — frontend, backend, database, data flow

**Frontend:** `/marketing` server component, reading persona and brand from
`lib/`. Content cards are client components only where they need copy/export
interactivity.

**Content logic:** `lib/marketing/` holds the persona, brand voice, seed
content, and the pure generators/validators — no React, no I/O — so tests
execute the same code the page renders. Same shape as `lib/pricing/model.ts`.

**Backend:** two route handlers.
- `POST /api/marketing/generate` — calls `claude-opus` with a persona-grounded
  prompt, returns labelled content. Null-safe: no key → returns seed content
  labelled `heuristic`, so the page never breaks (the `/core` pattern exactly).
- `POST /api/marketing/save` — persists a chosen asset, re-validated server-side.

**Database:** one new table `marketing_assets` (per-user RLS, mirrors
`pricing_scenarios`): id, user_id, kind (post|script|calendar|headline),
content jsonb, extractor, created_at. The A/B choice persists here or in
`user_prefs`.

**Data flow:** persona + brand → generate route → labelled cards → user picks
/ A/B tests → save route → `marketing_assets` → rendered back on load.

## 8. Tech stack

| Layer | Choice | Rejected |
|---|---|---|
| Content generation | Existing `@anthropic-ai/sdk`, `claude-opus` | A second AI vendor — no reason |
| Content storage | Supabase `marketing_assets`, jsonb | A column per content type — jsonb fits variable shapes |
| A/B mechanism | Deterministic pick + persisted choice | An experimentation platform — needs traffic |
| Export | Reuse `lib/export/csv.ts` (formula-injection-safe) | A new export path |
| Copy | `navigator.clipboard`, wrapped | A clipboard dependency |

**Net new third-party dependencies: zero, seventh week running.**
